## F. Web security headers (S1-12)

| ID | Decision | Source / reason | Status |
|----|----------|-----------------|--------|
| D-020 | Production security headers live in `apps/web/public/_headers` (Netlify / Cloudflare Pages format; copied to `dist/`): strict CSP (`default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; worker-src 'self'; manifest-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`), `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `Permissions-Policy` with camera, microphone and geolocation off, and for `/sw.js` `Cache-Control: no-cache` + `Service-Worker-Allowed: /`. `vite.config.ts` reads that same file for `preview.headers` (production policy unchanged) and `server.headers` (dev only). The dev policy is relaxed in exactly three ways, implemented by `devCsp` in `apps/web/security-headers.ts`: `'unsafe-inline'` on `script-src` (Vite's React refresh preamble is an inline module script), `'unsafe-inline'` on `style-src` (HMR injects `<style>`), and `ws://localhost:*` / `ws://127.0.0.1:*` on `connect-src` (HMR WebSocket). The production policy is never weakened. To keep the built site CSP-clean: no inline scripts, styles or style attributes (guarded by a test), and fonts are never inlined as `data:` URIs (`build.assetsInlineLimit` returns false for font files) because `font-src 'self'` would block them. `<meta name="referrer" content="no-referrer">` is added in `index.html`; a CSP is not delivered by meta. The service worker caches a static asset only if its Content-Type is not `text/html` (the offline page excepted), and `classifyRequest` bypasses any URL containing an encoded slash/backslash or double encoding (`%2f`, `%5c`, `%25`). Hosts that ignore `_headers` must reproduce the headers. Not verified in a real browser. | S1-12; security-review of S1 | proposed |

## G. Booking requests (S5-1 / S5-2)

| ID | Decision | Source / reason | Status |
|----|----------|-----------------|--------|
| D-021 | A booking is a REQUEST (`booking_status`: pending / confirmed / alternative_offered / cancelled / expired), never shown as confirmed until staff act (S6). The 201 response is the ONLY one that carries the reference and the independent 256-bit secret (base64url). Only an HMAC-SHA256 verifier of the secret is stored (`BOOKING_SECRET_KEY`; a fixed DEMO key is used only in DEMO_MODE). | Master prompt F06, section 8. | Implemented |
| D-022 | Idempotency: `Idempotency-Key` is required (16-128 chars). The same key and body within 24 h replays as HTTP 200 `{alreadyCreated:true, reference, status}` WITHOUT the secret (it cannot be re-shown; a client that lost the 201 must send a new request). The same key with a different body is 409. Keys are stored only as HMACs. Rejected requests (policy, validation) consume no key. | Avoids a second secret and a duplicate row. | Implemented |
| D-023 | Lookup is POST-only (`/public/booking-requests/lookup`, body `{reference, secret}`); failures are one generic 404 `lookup_failed` for unknown reference, wrong secret, malformed reference and expired requests. Throttle: 5 failures per 15 minutes per HMAC(reference) (known or unknown references alike), then 429 with Retry-After for 15 minutes even for the correct secret; plus a coarse in-memory per-IP limiter. Known trade-off: lockout can be triggered against someone else's reference (availability vs enumeration). | Section 8/11. | Implemented |
| D-024 | Minor policy adapter (`apps/api/src/booking/minor-policy.ts`, interface v1): under-15 always rejected; 15-17 rejected with `minor_policy_not_configured` unless evidence + clinic mapping + effective date AND `REAL_MINOR_BOOKING_ENABLED` (forbidden by env.ts). A DEMO fixture policy accepts 15-17 only in DEMO_MODE on a demo clinic and stores `is_demo_minor_flow=true`; the DB also forbids any non-demo-flow 15-17 row and any under-15 row. | F12; SOP artifact absent. | Implemented |

## H. Staff authentication and booking decisions (S6-1 / S6-2)

| ID | Decision | Source / reason | Status |
|----|----------|-----------------|--------|
| D-025 | **G-AUTH (open gap): dev-equivalent staff auth.** Supabase Auth is not available locally, so staff sign in against `staff_users` (scrypt N=16384 r=8 p=1, 16-byte per-user salt, timing-safe verify, one scrypt run even for unknown accounts) and get an opaque 256-bit session token in an `httpOnly; SameSite=Strict; Path=/api/v1/staff` cookie (`Secure` on every host except localhost). Only SHA-256(token) is stored; sessions expire absolutely after 8 h and after 30 idle minutes, and logout revokes server-side. Roles: `clinic_staff`, `clinic_admin`, `provincial_admin`, `technical_admin`; only clinic-level roles with an ACTIVE `clinic_memberships` row can read or decide that clinic's booking requests (admin roles hold no membership, so they are not booking readers). **What the dev equivalent does NOT provide and Supabase Auth must before any real use:** invitation/onboarding and secure password reset, MFA, password-breach and complexity policy, JWT claims consumed by RLS (`auth.uid()`), managed session/device revocation, and email verification. RLS policies for role `kalinga_staff` read the actor from the session setting `kalinga.staff_user_id` (set by the API; there is no client-supplied identity) instead of `auth.uid()`. These policies are exercised in tests (`set role kalinga_staff`) but the API itself connects as the owner and applies the same predicates explicitly on every request; production must run the API with a non-owner role. | Master prompt 2/A01; D-005, D-006 | Implemented as dev equivalent; **G-AUTH stays open** |
| D-026 | CSRF for state-changing staff routes: **session-bound synchronizer token** (not double-submit cookie). The token is derived from the secret session token, returned only in the login and `/me` JSON bodies, and must be echoed in `X-CSRF-Token` on every non-GET staff request (compared in constant time against the stored SHA-256). It is layered with an Origin check (an `Origin` header, when present, must be the request's own host or an allowed origin; `null` is rejected; login is covered too) and SameSite=Strict. Allowed extra origins default to the Vite dev origins in DEMO_MODE only. | OWASP CSRF cheat sheet; avoids a readable CSRF cookie | Implemented |
| D-027 | Login: one generic 401 `login_failed` for unknown account, wrong password, deactivated account and locked account. Lockout: 5 consecutive failures within 15 minutes lock the account for 15 minutes (the right password is also refused while locked; the lock is not extended by further attempts, and the answer does not reveal it). A per-IP limiter (30 attempts / 15 min) answers 429 `login_throttled`. DEMO accounts (`is_demo`, `@demo.invalid`) cannot sign in when DEMO_MODE is off. Known trade-off: the lock is a targeted denial-of-service lever against a known e-mail address, as with the booking-lookup lock (D-023). | OWASP ASVS 2.2 | Implemented |
| D-028 | Authorization failures on resources answer **404, never 403** (unknown clinic, another clinic, wrong role, malformed id and a request id from another clinic are indistinguishable); unauthenticated is 401; CSRF/Origin failures are 403. Membership and role are re-read from the database on EVERY clinic-scoped request (nothing is cached in the session), so deactivation or a role change takes effect on the next request. Denials write an `access_denied` audit row with no request content. | Master prompt section 8/11 IDOR | Implemented |
| D-029 | Booking decisions: `PATCH /api/v1/staff/clinics/:clinicId/booking-requests/:id/status` with `If-Match: "<version>"` (428 when missing, 409 `version_conflict` when stale, so of two concurrent confirmations the loser gets 409). State machine: pending -> confirmed / alternative_offered / cancelled; alternative_offered -> confirmed / cancelled; confirmed, cancelled and expired are terminal for staff (a visit that must be called off after confirmation is a clinic procedure outside this prototype); `expired` is set only by the `expireStalePending` system helper (pending older than 14 days or past its preferred date in Asia/Manila). Illegal moves are 409 `illegal_transition`. Visit and alternative times are Asia/Manila and must be in the future (within 180 days). Text is plain only (no control characters, no `<` or `>`; note single line <= 200, instructions <= 500) and is stored verbatim; the UI must escape on render (React does). | Master prompt section 5/8 | Implemented |
| D-030 | Public lookup integration without changing its contract: the lookup still returns only `clinicNote` and `visitInstructions`. The confirmed visit time (or the proposed alternative) is therefore also written, as a short generated English prefix, into `booking_requests.clinic_note` (`Visit time (Asia/Manila): 2026-11-05 10:00.` / `Clinic proposes another time (Asia/Manila): ... Not yet confirmed.`) followed by the staff's own note, while the exact instants are kept in new columns `visit_starts_at` / `alternative_starts_at` for staff views. The prefix is English only and unreviewed (localising it is a later task). | Keeps the S5 lookup response unchanged | Implemented |
| D-031 | `audit_events` is append-only (trigger), metadata is flat ids/statuses/versions/booleans from an application allow-list, and a CHECK constraint rejects metadata containing secret, token, password, e-mail, phone, reference, contact, hash, note, instruction or name. The status-change audit row is written in the same transaction as the decision. Reading the audit log is not exposed yet (S7). | Master prompt section 11 | Implemented |
